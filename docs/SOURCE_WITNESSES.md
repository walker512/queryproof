# Single-table source witnesses · 0.3.0

This optional mode links a generated query's actual results to **complete typed rows and locators in its exact SQLite snapshot**. Duplicate projected values retain separate source rows. A bounded `COUNT(*)` links its one result to the complete matching set, not a guessed representative row. This is a narrow, checkable workflow rather than arbitrary SQL lineage, natural-language interpretation or business-truth certification.

The original `queryproof.py`, its arbitrary read-only SQL CLI, old tests and `queryproof/1` receipt version **remain 0.2.0 and unchanged**. The distribution and new `queryproof-witness` mode are 0.3.0. Installing the new distribution does not silently upgrade old receipt semantics.

## Try rows and COUNT with an actual source

Python 3.11+, SQLite **3.37 or newer** for `table_list` introspection. No runtime dependencies or network. From the checkout:

```sh
python -m queryproof_witness run --csv sales=examples/sales.csv \
  --spec examples/witness_rows.json --out private-row-witness
python -m queryproof_witness verify private-row-witness
python -m queryproof_witness run --csv sales=examples/sales.csv \
  --spec examples/witness_count.json --out private-count-witness
python -m queryproof_witness verify private-count-witness
```

The original fictional CSV has two rows for customer `a`, amounts `10` and `20`. Rows mode returns those two rows with separate snapshot rowids and complete source values. COUNT returns integer 2 and both full source rows. CSV cells are **TEXT**, including amounts; their sort is text order, not inferred numeric order. An empty CSV cell is empty text, not SQL NULL. CSV witnesses locate rows in the imported SQLite snapshot, **not original CSV physical line numbers**, which can differ with headers/quoted multiline fields.

For an authorized existing database:

```sh
queryproof-witness run --db local.sqlite --spec selected-rows.json --out private-witness
queryproof-witness verify private-witness
```

The installable `queryproof-witness` entry point works without the repository as the current directory. The old `queryproof` command remains available. Inputs/outputs stay local; no account, upload or agent is involved. Output directories must be absent and their parent must already exist.

## Explicit supported spec

A spec has exactly `schema`, `table`, `mode`, `project`, `filters`, `order`, `limit`, `offset`; use the two bundled examples. Names must match introspected table/column names exactly. All clauses are generated by this module with safely quoted identifiers and bound parameters. There is no SQL-fragment field or arbitrary-SQL parser.

- `rows`: a nonempty list of unique projected columns, 1..10,000 limit and integer offset 0..10^9. `order` is zero or more unique column/direction/nulls entries. With no user order, the snapshot-local locator orders results deterministically.
- `count`: only **COUNT(*) over the entire WHERE-matching set**. Projection/order must be empty and limit/offset null. No `count(column)`, distinct, GROUP BY, SUM, joins, unions, expressions, custom functions or nested subqueries.
- Up to 32 predicates, combined with AND. `eq`, `ne`, `lt`, `le`, `gt`, `ge` require a typed literal. `is_null` and `not_null` require `literal: null`. OR/fuzzy text/coercion semantics are deliberately not inferred.

A typed literal is `{"type": "integer", "value": 12}`, or type `text`, `blob`, `real`. Integers are signed 64-bit and JSON booleans are not integers. Text is exact Unicode (empty text is allowed). BLOB literals use canonical base64. Real literals use an explicit **finite binary64 `float.hex()` string**, for example `{"type":"real","value":"0x1.8000000000000p+0"}` for 1.5. Decimal JSON floats, NaN/Infinity and noncanonical real representations are rejected. This makes the bound SQLite double explicit; it is not arbitrary-precision decimal arithmetic. SQLite may normalize representations such as negative zero when storing values. The witness records the values actually read from SQLite, not claimed original file encoding bits.

Every non-NULL filter checks `typeof(column)` equals the declared storage type, then compares a unary-plus expression with the parameter and explicit `COLLATE BINARY`. Unary plus removes the column's declared affinity. Thus an integer filter does not silently match text `"1"`, and a column's NOCASE collation does not turn `A` into `a`. NULL only matches the explicit NULL predicates; `ne` does not include NULL. This intentionally differs from ordinary SQLite coercion/column-collation behavior. It is the declared contract of this mode, not a claim that it matches the user's intended business logic.

Relevant official references: [SQLite storage types and affinity](https://www.sqlite.org/datatype3.html), [PRAGMA table_list/table_xinfo](https://www.sqlite.org/pragma.html#pragma_table_list). A column's declared type is not proof of each stored value's actual type.

## Locators, ordering and pagination

Only one ordinary user table is supported. Views, virtual tables, virtual shadow tables and any table with generated/hidden columns are conservatively rejected. SQLite introspection, not substring parsing of CREATE TABLE text, determines table kind, WITHOUT ROWID status, columns and PK order. Unsupported/older introspection fails rather than guesses.

- Ordinary rowid table: choose the first unshadowed alias among `rowid`, `_rowid_`, `oid`, comparing actual column names case-insensitively. If all aliases are shadowed, reject the table even if a human might identify a usable key.
- WITHOUT ROWID table: use the complete introspected non-null primary key in declared key order, including composite keys. Every key value carries its actual storage type.

**Locators identify only rows in this exact snapshot.** They are not durable identities across VACUUM, other databases, edited sources, reloads or versions. Full source values accompany each locator, including columns the user did not project. Repeated output values therefore remain independently inspectable.

For each explicit ordering column, NULL placement is first/last as requested. Non-NULL storage classes are grouped in fixed ascending order: integer, real, text, blob. Within a class, value order uses the requested ASC/DESC; text uses BINARY. This is not a mixed-numeric global sort: integers and reals remain separate classes even for DESC. The locator is appended as an ascending deterministic tie-breaker using the same type-aware/BINARY convention. Projection order follows `project`, source-value order follows the recorded complete schema.

Rows mode records total WHERE-matched count, included witness count, half-open captured ordinal range and number of matching rows not included. Limit/offset remain in the exact spec and generated query parameters. A page is not passed off as the full matching set. Offset beyond the end yields an empty page with start/end clamped to matched count; the original requested offset is still visible in the spec. Witness ordinal zero corresponds to result row zero of the returned page.

COUNT mode returns one result row. All witnesses together form that count's source set, ordered by locator for inspection. Empty matching sets yield count 0 and an empty complete witness set. Above 10,000 matching rows or the evidence-byte cap, the command **rejects** the COUNT bundle rather than returning a number with a silently truncated source list. It never substitutes one source row for an aggregate.

## Actual query/result linkage

After creating a consistent snapshot, the module opens a single read transaction. It introspects schema, runs the matching-count query, runs the full source/locator witness query, and independently runs the generated projection or COUNT query. For rows, typed projected values must match the corresponding complete witness-row projections in order. For COUNT, the SQL answer must equal the length of the complete source collection. A mismatch fails creation. Only SELECT/READ of the selected table and required built-in functions are authorized after schema introspection; no DML or user-supplied execution is added.

The result/locator/source values use explicit tags: null, integer, real hex, text, BLOB base64. Invalid UTF-8 and nonfinite stored real values in included rows are rejected. Invalid values outside a requested page may remain in the full snapshot and are not claimed reviewed. NULL/empty-text diagnostics cover **included complete source rows only**. This new mode does not silently claim the old whole-snapshot profile, key checks or JOIN-cardinality diagnostics. Use the old mode for those distinct features.

## Bundle, recomputation and privacy

A complete bundle contains exactly:

- `snapshot.sqlite`: the **entire** source database snapshot, not just selected rows.
- `spec.json`: original exact specification bytes.
- `queries.json`: generated result/witness/count SQL and explicitly typed bound parameters.
- `witness.json`: result rows, full source rows, locators, coverage and scoped diagnostics.
- `receipt.json`: file hashes, source descriptions, limits and environment/build binding.
- `report.html`: an escaped static display of queries, evidence and receipt, with restrictive `default-src 'none'` CSP and no scripts, embeds or external requests.

**The complete snapshot, full source rows, filters, metadata and typed BLOB content can disclose much more than the visible result.** Nothing is anonymized, encrypted or redacted. Inspect before sharing. HTML values are escaped, not treated as active markup; this is a static review document, not a newly browser-accepted GUI. No CSV/XLSX formula protection or publication is implied.

SQLite snapshots reuse the old online backup mechanism, including committed WAL data while a source writer remains open. Only the newly owned private backup is normalized to DELETE journal mode before querying, so its immutable bundle has no live WAL/journal dependencies. The original live database and its sidecars are not changed or deleted. CSV import likewise reuses the original consistent import rules.

Verification rejects extra files, live sidecars and symlink/special-file leaves, reads bounded bytes into a private copy, checks snapshot/spec/receipt binding, re-introspects and reruns the same transaction, and compares generated queries, all witnesses/results and deterministic report bytes. SQLite version, source ID/build options, legacy core version and witness version must match the receipt. Python/OS metadata is retained as information, not a portability guarantee. The source database/CSV is not needed or reopened during verification. CSV source hashes cannot be rederived without the original CSV bytes; they are retained import descriptions, not authenticated external provenance.

A fully coordinated rewrite of snapshot, spec and evidence can produce another consistent bundle. Hashes are not signatures. Verification cannot establish source truth, actual business semantics, completeness of a user's chosen filters, authorship or cross-snapshot identity. No natural-language/AI explanation or arbitrary SQL lineage inference is performed.

## Bounds, publication and limitations

Source/snapshot maximum 32 MiB; 1 MiB spec; up to 32 CSV tables; 128 ordinary columns; 32 AND predicates; 16 order keys; 10,000 returned/witness rows; complete evidence including results capped at 4 MiB; every generated non-database file capped at 16 MiB. The underlying connection limits each SQLite value to 1 MiB and generated SQL to 64 KiB. The new transaction uses a two-second SQLite progress deadline, not an OS wall-clock sandbox. Existing backup progress budgets remain in effect. Native SQLite/OS operations and malicious environments are outside these bounds' security guarantees.

All source-derived artifacts are serialized and size-checked in a temporary directory and internally verified before publication. An absent destination is exclusively reserved and the same-filesystem directory is replaced atomically on the tested POSIX environment. Existing even-empty directories are refused. No old output is overwritten or unknown directory recursively deleted. Power-loss durability, hostile parent-directory replacement and adversarial file races are not certified. Inputs must be authorized, regular, local files; this is not an untrusted database upload service or a native SQLite sandbox.

Exit 0 means creation or internal recomputation succeeded, including empty results. Exit 2 means controlled input/storage/schema/bounds/recomputation failure. Diagnostics omit source values/SQL/private paths. The old CLI retains its own exit codes and structured failure diagnostics; it is unchanged. Windows/macOS and new-mode browser acceptance are not claimed.
